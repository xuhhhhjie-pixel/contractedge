## 二、与任务书的偏离（需要确认）

1. **行为状态放在宿主侧**（不挂载进容器的目录），所以没有做容器内 inbox 请求文件、`ce-graph behavior` 子命令和 `submit.py` 汇总。理由：模型在容器里有 shell，状态放容器内它能直接改；宿主本来就是单进程顺序执行。
2. **只用已有 Go 测试做检查**，不由模型生成新检查脚本；只有 `go test -json` 一个适配器。
3. **改造四未实现**，打开 `behavior_impact` 会直接报错。
4. **`/inputs` 当作公开来源使用**（任务文本声明公开输入只读挂载在 `/inputs`）。是否认可需要老师确认；若不认可，删掉白名单里的 `/inputs` 即可。
5. 在原始版本上的校准只在检查恰好于编辑前运行时发生，没有单独回到原始版本跑一遍。

### 机制层面看到的

- **要求提取能用**：每次在 6–65 秒内给出 2–6 条要求，引文全部核对通过，没有出现被拒的虚构引文。

- **最大的时间开销是冷构建**：公开运行时的 `GOCACHE` 是每次 `ce-run` 都会丢掉的 tmpfs，模型自己跑的每次 `go build / go run / ce-public` 都要从头编译（UPJET 约 250 秒）。这是两组共同的环境问题，不是行为方法独有的。
- KEDA 运行中模型花了几步用 `git cat-file --batch-all-objects` 查看仓库对象，找到的是方法自己的自动检查点（`refs/ce/ckpt/1`，内容就是它自己的修改），不是答案泄露。

## 四之二、示例检查与对照实验（2026-11-12 下午）

### 动机

上午的冒烟里检查一次都没跑：两个案例都没有能覆盖目标的已有测试。而公开夹具常给出"触发/对照"具体案例（153 例中 56 例带夹具）。因此新增开关 `behavior_examples`（变体 `behavior-examples` = `behavior` + 示例检查）。

### 机制（`behavior_examples.py`）

- 要求提取同时给出"示例"：案例名、target/preserve、要观测的字段；字段期望值能在公开材料里逐字找到的记为 LITERAL（由程序锁定），否则为 DIFF（target 须与原版不同、preserve 须与原版相同）。
- 驱动程序由**执行器**按协议写在 `/testbed/.contractedge-deps/ce-examples/`（不进补丁），打印 `CE_OBSERVE` 行。最初的设计是由独立小助手先写，真实运行中 16 步都只够读代码（UPJET-AWS-2182、GCP-1015 各 1 次），改为执行器写；独立助手保留为可选开关。
- 驱动出现或改动时，在**原始版本副本**（`git archive` 基线树到被排除的目录）上校准：字段必须被观测到；LITERAL target 在原版上不能已经相等（写死答案会被剔除），LITERAL preserve 必须相等。之后每次编辑自动重跑，报告"观测值对期望值"；提交前有未看过的失败或"有示例但没驱动"各提醒一次。
- `-trimpath` 让原版副本与当前版本共用构建缓存：原版首次 261 秒，之后两边都约 4 秒（实测）。
- 另修：要求提议遇到空回复重试一次（实测 DeepSeek 偶发 0 字符回复）；DSML 格式的命令可被识别。
- 测试 180 项通过。

### 案例与结果

按事先写定的规则选案例：全量基线里 Live 未成功、Go、development 划分、带公开夹具、我未读过判据 → R4-PROVIDER-UPJET-AWS-2182、R4-PROVIDER-UPJET-GCP-1015；另加已读过判据的开发例 UPJET-AWS-2117（单列）。前两例零模型重新准备（各约 15 分钟）。

| 案例 | behavior-examples | 试点（驱动未写成，近似 behavior） | submit-only |
|---|---|---|---|
| UPJET-AWS-2117 | SEMANTIC_FAIL ×2 | SEMANTIC_FAIL ×2 | SEMANTIC_FAIL（上午） |
| UPJET-AWS-2182 | 空补丁（预算耗尽）、INVALID_PATCH | PASS | INVALID_PATCH |
| UPJET-GCP-1015 | PASS、空补丁（模型请求读超时） | SEMANTIC_FAIL | PASS |

12 次运行约 13.5 元（其中 1 次计费缺失，按约 1.4 元估）。**两组通过率无可见差异，不能说明行为方法提高了修复率。**

### 拆开看

1. **强制提交带入临时文件**：2182 的两个 INVALID_PATCH（一组一个）都夹带了执行器自己的临时文件（`.ce_candidate.go.mod`、`tmp_diag/main.go`；`.probe/main.go`、`probe_diff.go`），且都是墙钟 85% 强制提交、绕过了提交检查。只保留政策允许的文件后诊断重评，**两者都是 PASS**。这是提交机制的缺陷，两组共有。
2. **几乎所有运行都撞墙钟 85%**：冷构建每次 200 秒以上。
3. **示例机制在真实运行中首次跑通**：UPJET-2117 两次运行中执行器写了驱动，原版校准后自动重跑，trigger 的 external_name 从与期望不符变为通过，control 保持通过。但隐藏判据还要求 Terraform ID 的反向映射等于状态 id；示例没有覆盖这一"往返"关系（驱动把输入的 state id 原样打印，校准正确地剔除了该字段，执行器没有修驱动）。
4. **新机制的成本**：2182 有一次执行器把时间用在写、改驱动上（两次校准都因字段没观测到被拒），到墙钟 85% 时源码未改，最终预算耗尽、空补丁。

目的：判断"执行器拿到正确、可执行的行为反馈后能否修对"。在已读过判据的两个开发例上，用发布包隐藏评测的行为桥改写成驱动、期望值取判据（`gold` 注入，仅用于上限实验，不是方法成绩），其余流程与 `behavior-examples` 相同；基础组为 `submit-only`，两组都开去噪声。

| 案例 | 金标组 | 去噪声基础组 |
|---|---|---|
| UPJET-AWS-2117 | **PASS ×3**（818–1466 秒，均正常提交，示例全部通过） | SEMANTIC_FAIL ×2 |
| KEDA-7777 | **PASS ×3**（3 次都在墙钟 85% 强制提交，提交时示例全部通过） | SEMANTIC_FAIL ×2 |

- 方法组多了 1 个通过，**样本太小，不能说明修复率提高**；这只是开发例上的趋势。
- 2182 是方法组明显占优的一例：3 次都通过，其中 2 次在 65% 时间触发了退回保护（驱动没写成，执行器转去修复）。可见退回保护避免了示例实验里"空补丁"的情况。
- 3 次运行因为传输层的累计 token 预算中止（`CUMULATIVE_TOKEN_RESERVATION`）：方法组 2 次、基础组 1 次。两组 token 用量相当，这是共有的预算限制。
- **2117 方法组失败的直接原因是提取给了错误的期望值**：第 1、2 次把 trigger 的 `external_name` 期望写成了状态 id，而该示例自己引用的夹具行写的是 `"external_name": "vpce-…/subnet-…"`。错误值在材料里确实出现过，所以通过了逐字核对；执行器把代码改成了符合这个错误期望的样子，示例全过，判据失败。也就是说，**错误的示例会主动误导**（R-A 的风险）。
- KEDA：提取只能给出"创建 HPA 与否"这类差异字段，判据要求的具体错误文本不在公开材料中（判据过度指定，见案例审计）。L2 用金标字段名直接给出了错误文本，所以能通过。

### 第 4 轮：字面期望值与引用记录一致

字面期望值如果和该示例自己引用的记录（JSON 或 YAML 行）中同名键的值冲突，不作为字面期望，降级为"必须与原版不同"，并记录原因。对 2117，降级后的引导正好是正确方向：原版给出状态 id，修复后必须变成别的值。测试 193 项通过。

2117 方法组复跑 3 次：**仍为 0/3**（SEMANTIC_FAIL ×3，4.07 元）。

- 冲突检查生效：第 2、3 次把错误的 `external_name` 期望拦下，降级为"必须与原版不同"。第 1 次模型把同一个错误值放在另一个字段名 `derived_external_name` 下，冲突检查拦不住；但这个字段在校准时因"原版已经等于期望值"被剔除，没有误导执行器。
- **新发现的根因：驱动选择的输入和判据不同。** 第 1 次提交的版本里，往返字段 `rebuilt_identifier` 在示例上通过，判据却观测到 trigger 的 terraform_id 是 `vpce-…/subnet-…`。原因是执行器的驱动把"从状态导出的名字"当作 GetIDFn 的输入，判据用的是夹具里的 external name。执行器把配置改成了 `IdentifierFromProvider`，在它自己选的输入上前后一致，却不是正确修法。示例的"输入"目前只是一段文字，执行器可以自由选择。
- 下一步：示例输入要**固定成公开记录本身**。由方法把示例引用的记录写进骨架或输入文件，驱动只能读取它；校准时核对驱动确实用了这些输入。

### 小结

| 改动 | 证据 | 效果 |
|---|---|---|
| 名字规范化、提示词（双向映射、文本描述的情况、只要输出） | 离线提取 | 提取覆盖明显提高（见上表） |
| 退回保护 | 开发集 2182 | 2 次触发后仍通过；未再出现因写驱动耗尽时间的空补丁 |
| 校准窗口、骨架、驱动输出反馈、名字容错 | 单测、骨架用真实 Go 编译运行 | 方法组 12 次中 5 次校准成功；下午示例实验中执行器写驱动的 6 次里只有 2 次成功 |
| 冲突检查 | 2117 复跑 | 错误期望被拦下，但 2117 仍未修对（输入未固定） |
| 合计 | 开发集 12 对 12 | 方法组 5/12，基础组 4/12；差异在噪声内，**不能说明修复率提高** |

## 五、未验证与已知风险

1. **检查—反馈链**：已有测试检查在真实模型下仍未运行过；示例检查链已在真实运行中跑通（见上），但没有带来可测的修复率差异。
2. **修复率没有任何结论**：上午 5 次 + 下午 12 次，案例少、每组次数少，结果在噪声内。
3. **提议超时没有真正生效**：配置 30 秒，第二轮 UPJET 的要求提议实际 64.7 秒。传输层带重试，超时只约束单次尝试。
4. 检查缓存每个工作区约 1.3G（UPJET），工作区清理时一并删除；正式实验要算进磁盘准入（服务器当前剩余约 80G）。
5. Ginkgo、Helm、kustomize 等测试形式首轮一律不支持。
6. 预算参数（3 次计划、每步 1 次检查、提交前 2 次、120/420 秒、12 次）都是暂定值。

## 六、需要学长 / 老师定的事

1. `/inputs`（含夹具）能否作为方法的公开来源。本版已经在用，并且是目前唯一有效的目标信号来源。
