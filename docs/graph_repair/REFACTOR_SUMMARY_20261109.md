## 一、原来的问题

### 1.1 旧版 ContractEdge 输在动手之前

| 发现 | 数据 |
|---|---|
| 多数运行停在编辑前 | 32 次运行中 19 次停在编辑前；进入编辑的 13 次中 10 次通过 |
| 前期检查是主因，不是截断 | 给全正确位置的源码，仍只有 2/12 走到修改计划；放开残余缺口后上限组到 9/12 |
| 修了检索又被额度卡住 | 首轮交付 10/12，但 7/12 调用耗尽，只有 3/12 走到修改计划 |
| 与强基线差距大 | 12 例面板上 Live 通过 11/12，旧版 ContractEdge 4/12 |

结论：“诊断 → 计划 → 受限编辑”的多段链路太长、关卡太多，交接时丢信息。

### 1.2 通用方法（Live）真正做不好的地方

基线全量运行（450 个位置）差异分析显示，Live 失败 28 例，其中：

- **改错 9 例**：公开检查信号弱，或破坏了原有行为；
- **修对却没提交 8 例**：补丁已正确，但没有发出提交标记；
- **违反提交规则 6 例**：改了 `patchable_paths` 之外的文件，补丁被拒；
- 三种方法都没修对的 26 例中，17 例没有任何正确补丁。

因此重构方向是：不再在编辑前设关卡，改为在 Live 同一框架上加“契约图 + 提交机制”，把价值放在改得是否完整、有无回归、修对后能否及时提交。

## 二、做出的改进

### 2.1 方法与实现（方案第二版）

| 部分 | 做法 |
|---|---|
| 执行器 | mini-swe-agent 1.17.5 `DefaultAgent` 的子类 `ContractGraphAgent`，只重写 `execute_action` 与 `has_finished`，核心循环、容器、挂载、补丁导出都与 Live 相同 |
| 提示 | `livesweagent.yaml` 原样，只替换 “Recommended Workflow” 一节 |
| 容器内工具 | `ce-search/read/follow`、`ce-links`（Helm、Kustomize、Go 标签、CRD、环境变量与 flag、依赖 API）、`ce-graph`、`ce-closure`、`ce-probe`、`ce-ckpt`、`ce-rollback`、`ce-submit --check`；只读挂载 |
| 自动检查点 | 私有索引 `write-tree` + `commit-tree`，不动 HEAD、真实索引和工作区，不进入补丁 |
| 自动连接与闭包 | 首次修改某文件后自动运行连接器，列出同一声明的其他消费者作为闭包候选，附在观察里 |
| 提交检查 | 模型发出提交标记时自动检查：提交规则（与发布校验器同为 `fnmatchcase` 语义）、闭包决定、公开检查、已校准探针；未满足项返回模型 |
| 强制提交 | 墙钟 85%、传输层 token 余量不足两次请求、或连续两次未满足项相同时，提交最好的检查点 |
| 消融开关 | A 完整、B 同期重跑 Live、C 无探针、D 无闭包、E 无停止规则、F 仅提交检查与强制提交、Z 全关 |

### 2.2 已完成的验收

### 2.3 过程中发现并修复的问题

| 问题 | 修复 |
|---|---|
| 模型从不主动使用契约图工具（面板第一轮 5 次运行均未调用） | 连接器与闭包改为执行器自动机制 |
| 提交规则用了 shell 通配符语义，把真正的修复文件判为不合规 | 改为与发布校验器相同的 `fnmatchcase` |
| 被传输层 token 上限截停时没有提交 | 新增 token 余量触发的强制提交 |
| `ce-links` 在大仓库（17012 个文件）上超时 | `git grep` 预筛选、25 秒预算、导航器惰性哈希 |
| 同案例并行导致结算断言失败 | `complete_slot.py` 零模型补全收尾；关闭同案例并行 |
| 主机高负载打断运行 | 作业超时 2400→4800 秒；中断运行按 wire 账本计费并记为基础设施问题 |
| 容器子 uid 写入的文件宿主机删不掉 | 改为经容器删除，失败只记录不中止 |

### 2.4 M5 改为小规模试跑

原计划 M5 为 272 次运行。由于方法进入 M5 前刚改了三处、且只在面板（多为 Live 能修好的案例）上验证过，改为先试跑：A1 与 B1 各 1 次，14 个案例，按冻结名单顺序从各类别取样。

1. **新方法在试跑上胜过同期 Live**（7/14 对 4/14，胜 3 负 0）。B 在“未提交”和“违反规则”两类上重现了基线中的失败，说明这两类是 Live 稳定存在的问题，不是偶然。

## 五、现在的计划

### 5.1 先做的低成本验证（约 6–8 元）

在试跑同一批 14 例上补跑 **F1**（Live 只加提交检查与强制提交）。这能直接回答“增益中契约图与提交机制各占多少”：若 F ≈ A，则增益确实全在提交机制；若 A > F，契约图有贡献。同时补跑 2 次被基础设施中断的 A1。

### 5.2 方法调整（针对“改错”类）

目标是让契约图在改错类上真正起作用：

1. **需求覆盖检查**：提交检查中对照任务描述列出的行为，要求模型说明每一项由哪处改动覆盖；
2. **自动保持探针**：修改某个包后，自动运行该包已有的单元测试作为回归探针，不依赖模型自己写探针；
3. **渲染级探针自动生成**：Helm/Kustomize 改动后自动渲染模板并比较关键字段，作为跨工件一致性检查；
4. **成本控制**：提交检查全部满足时提示尽早提交，减少跑到墙钟兜底。

**开发用案例**：只用面板 12 例和评测名单之外的案例，**不看评测名单中“改错”案例的失败细节**，避免污染评测。
