# 冻结验证发现的剩余问题与协作修改边界

本页记录冻结候选 `15141db3` 的真实失败与后继修改方向，不代表这些后继修改已经实现。原四个工作包及十一项编号保持不变；它们的实际完成情况见 [逐项验收](ISSUE_CLOSURE_MATRIX.md)，最终成绩以状态和真实验证报告为准。不能把新发现加入本次冻结版本后，继续沿用其工程或模型成绩。

公开回执：[候选池截取回放](CERTMANAGER_POOL_REPLAY.json)、[纠错反馈筛选回放](ALERT_CORRECTION_FILTER_REPLAY.json)。二者均未调用模型、未修改生产源码，只证明对应管道行为，不证明后继修复率。

## 1. 明确点名的函数在候选池截取时丢失

**已确认的事实：** Certmanager 扩容组的第二次取材明确请求 `lookupCNAMETarget` 及其目录。相同初选与查询回放中，该声明排第48，原40条池在最终排序前将它排除。扫描找到函数不等于候选池保留，更不等于请求送达。新版原容量成功组实际送达了582字节的函数正文；扩容组的总材料更多但缺这一项。

**修改入口：** `src/contractedge/source/units.py::extract_gap_extension_units` 的池截取；复用其已有声明身份、同一缺口的路径限定与查询信息。不新增检索服务或模型标签。

**具体做法：** 在原池额度内，先分配同范围内明确点名的声明，再使用当前跨文件分配容纳普通匹配。不能让注释、调用者、相似名称仅凭文本命中越过声明；也不能把模糊查询自动认定为唯一绑定。多个缺口共用有界池，冲突和未纳入项必须可检查。优先级本身不授予编辑权限、不生成因果证据，也不绕过最终整体准入。

**验收：** 保留原查询反例；同名不同receiver、跨目录同名、注释命中、多缺口争抢及超额度均有正反例。确认在同40条上限下目标声明进入池并被下游送达；再单独比较真实整案结果。不能把200条诊断探针当作正式解决方案。

## 2. 依赖查询入口过窄，已发送的只读API用途又不清楚

**已确认的事实：** Helm旧版／扩容组请求的API名与当前调用点不精确相交，未进入依赖读取；新版原容量组实际收到了三条完整API，仍继续索要相关选项。两种失败不可合并成“没传全文”。

**修改入口：** `source/dependency.py::gap_dependency_support`、`diagnosis/prompt.py` 及现有 `adopted_source_context` 投影。

**具体做法：** 以当前源码真实导入、调用点和固定依赖版本为读取依据。若查询点名已绑定的包别名，可以从实际使用的入口查其参数类型及相关工厂，而不是要求模型提前准确猜到尚不知道的API名。保持已存在的包数、记录数、字节数、完整扫描与shadowing检查；不允许查询选择任意外部包。消费者说明应明确既有只读API材料可以用于理解与规划，但不可伪装成仓库因果证据或可编辑目标。

**验收：** 真导入／假导入、别名遮蔽、版本不符、歧义入口和完整性失败均有检查；用相同已准备材料验证消费者是否能识别实际可用API。分别报告发现、送达和使用，不以新增提示词代替代码路径验证。

## 3. 搜索已有函数没有回答所需操作是否存在

**已确认的事实：** CloudWatch缺口同时指定已有helper和操作搜索词。当前 `locate_gap_roles` 优先取symbol，`collect_absence_search_evidence`只为准确path／symbol生成搜索事实，因此记录证明的是helper存在，没有回答目标操作的查询。

**修改入口：** `retrieval/gap_delivery.py`、`source/absence.py` 和runner既有取材入口。

**具体做法：** 复用现有定位字段区分“到哪里看”和“查什么事实”，避免前者覆盖后者。对明确字面标识符可以在同一有界搜索中生成准确的查找记录；保留范围、实际扫描量和完整性。文件内没有字符串只说明该范围内没有该字面命中，不能升级为全仓库不存在语义角色，也不能自动授权新建或改成READY。

**验收：** 同时带symbol与search_term、单字段、多个标识符、存在／不存在、部分扫描、路径变化和大仓库上限；检查请求收到的事实确实对应原问题。新增helper仍通过现有证据和编辑权限校验。

## 4. 诊断／计划协议仍可能阻断有材料的修复

KPT4746已收到四段关键函数，仍要求可能属于待新增实现的交接；KOPF失败组要求修复后的成功观察；KPT4673保留同容量退步，其关键函数没有被证实挤掉。Alertmanager新版原容量已编辑一次，续修时又出现前提来源ID和验证场景不一致。不能仅凭这些结果说案例无解，也不能全部归为取材不足。

**修改入口：** `diagnosis/prompt.py`、`changeset/prompt.py`、`changeset/validate.py`、`contracts/validation.py` 及既有有界纠错入口。

Alertmanager已有进一步的原回复离线反例：`_prerequisite_input_issues`能够在第一次计划中检出 `PRECONDITION_REVIEW_INCOMPLETE`，但runner调用 `compact_validation_feedback` 时仅额外纳入establishment两类错误；存在schema错误时，已知的独立身份错误被过滤。回放输出与实际纠错消息相同。后继应将已安全检查出的前提身份问题一起反馈，保持原有总条数和纠错次数，而不是等一次格式纠错后再暴露它。场景关联依赖合法结构，须继续区分可独立检查与依赖前序结构的错误，不能无条件打开全部深层校验。

同一请求还含有同快照、同行范围、同正文与摘要的 `SRC-CU-HELPER-…` 和 `HELPER-…` 两条材料，前提只接受后一身份。正文未丢失，但接口存在重复表达负担。可以为同一物理材料建立明确的展示别名，保留已采用原引用身份；不能靠字符串去前缀猜测两条证据相同。

**具体做法：** 先核对完整请求和最后一次纠错回复，区分必须澄清的事实、需要ChangeSet提出的新实现、需要运行后才能验证的结果。程序提供精确可选身份和适用场景，模型负责原因、意图与保持要求。若简化重复身份表达，应采用一份规范身份来源并验证完整引用链；不能通过随意去前缀、自动映射近似ID或删除校验来掩盖错误。合法未知继续保留，已有纠错次数不因单案失败增加。

**验收：** 使用原始失败请求与通用正反例；错误身份／错误场景仍被拒绝，合法计划可以进入编辑，待实现行为不被要求预先提供成功观察。模型策略变化须独立冻结并做真实对照；一次合法回复不等于整案通过。

## 共同边界

- 维持 Diagnosis → ChangeSet → TopoMen 分工；大部分后继修改仍在三者之间的材料与控制接口。
- 精确读取优先于增加文本总量；所有已采用和仍引用的正文继续完整传递。
- 当前多数组失败发生在执行前，TopoMen无限搜索／无限续修没有依据。有限自主读取实验仅在执行后的共同失败支持时另行比较。
- 每个后继版本保留原冻结、原失败和费用历史，记录实际diff、修改前反例、修改后工程检查与模型结果。不得修改当前面板的源码、配置、样本或评分去制造收益。
- 此处是修复方向和验收条件，尚无证据保证全部模型失败都能消失；正式准入需要稳定的成对收益和可解释的退步，无需150例全部成功。
