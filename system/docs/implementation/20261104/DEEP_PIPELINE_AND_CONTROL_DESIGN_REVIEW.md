**3. “证据缺口”到底指什么**

它应当表示：要支持某个诊断或修改决定，仍缺少一条可以核对的事实。它不是“模型还不放心”的无限搜索许可，更不是所有停止原因的统一名称。

例如：已看到配置入口和客户端构造器，却不知道配置值通过哪个调用传给客户端。这时缺的是中间传递关系，可以用现有 `summary` 说明具体问题，用 `locator_hint` 指向路径、符号或搜索词。无需增加一套缺口标签。

| 实际缺的是什么 | 应如何处理 |
|---|---|
| 未找到真实调用者、声明或固定版本 API | 复用取材入口，定向读取真实快照，返回完整声明。 |
| 已找到，但首次摘录不完整 | 在首次采用前补完整语法单元；不把前缀冒充整函数。 |
| 已找到完整材料，但发送前放不下 | 报实际容量或交付阻断；不能说成模型没找到。 |
| 材料已收到，但模型仍无法支持关系 | 让诊断说明具体尚不成立的关系；有界纠错或补查。不能由程序编造因果关系。 |
| 本来需要新增实现，仓库不存在该函数 | 利用已有精确缺失搜索与 EXPECTED_MISSING 协议，在调用点、接口和权限有依据时进入新建计划。不能无限寻找不存在的旧实现。 |
| 代码已修改，但公开检查尚不能证明目标行为 | 保留验证未完成或观察不足；增加源码未必解决。不要把编译通过升级为语义成功。 |

当前已有内容身份比较：`runner.py:1509,1609` 按 snapshot、locator、digest、正文判断是否真的增加材料；换 ID／换角色不算进展。这个机制应复用，不能再造一个“进展分数”。空提示应在消耗取材额度之前被现有格式纠错处理。证据已经送达而推理仍失败，不应再次归罪于压缩。

**5. Solver 规则的可靠性来自什么**

原规则的保护动机合理：真实源码注释可能否定一个看似可行的修改，例如更新操作会忽略 token。错误在于把“值得检查”提前等同于“必须送达”。

最小设计分清三个事实：名字匹配只用于发现与排序；明确指定的端点以及已采用材料必须保留；已送达的约束是否适用，由 ChangeSet 结合真实源码判断。现有 REQUIRED／UNRESOLVED／NOT_APPLICABLE 表达继续使用，不新增字段，也不自动替模型填 NOT_APPLICABLE。

仅修改 required IDs 的合并不够，角色合并还可能恢复强制性，所以两条路径都要修改。此次十项纯函数设计模拟覆盖：纯contract、纯reader、两种提示叠加、显式required、anchor、legacy必需、可选connector、lifecycle、纯提示合并、anchor合并；拟议规则保留真正强制项。仍需生产实现后验证真实跨阶段正文、适用性重算和初始／补证两条入口。

这证明设计有清晰边界和可测试性，不证明 Certmanager 的 Solver 一定无关，也不证明该修改必然提高修复率。Cert 的直接阻断仍是已经测实的支持容量。

**6. 完成、续修、回滚应该如何决定**

附件中的回箭头只是旧说明图的简化。实际代码已有回到执行、规划、诊断三条路，不应把每次失败都退回 Diagnosis。

目前 `feedback.make_feedback` 先给 route，后续无进展重审函数可以改 route，`repair` 还有前置条件重审与恢复候选优先级，`transitions` 多处消费已有 route。因此“已有 transitions 文件”不等于“所有决定已经集中”。这些分支有部分是必要保护，不宜直接删除。

此次还核实了一个需要单独验证的策略重叠：`feedback.py:219–251` 允许两个目标从“都失败”变成“一项通过”后继续执行；但 `repair.py:342–353,867–875` 只要计划含某项 REQUIRED 前提且仍有必要条件失败，就可能把下一步改成重新诊断，没有核查失败条件是否关联该前提。纯函数反例中，前提只引用已经通过的检查，重诊判断仍为 True。这证明策略覆盖存在，尚不能证明真实效果下降。建议利用现有 `verification_refs`／检查关联收窄触发条件，并以实际循环测试验证，不能新增语义分类器猜因果。

另有固定 profile hook 的 `repair.py:1214–1226` 可在仍有 pending 时写出 UNKNOWN 与 `next_action=COMPLETE`。实际调度与终态投影仍保持 UNKNOWN，默认 BenchmarkPublicRunner 也不普遍提供该 hook；这是展示字段一致性缺口，不是新的假 PASS。后续应从同一最终决定生成这几个字段，不再分别计算。

建议统一顺序：先保存当前试验的真实检查事实；再比较当前候选与上一可保留候选、必要时恢复文件；最后根据选中快照及失败试验的历史证据决定下一步。模型 reviewer 的 failure_kind 是低置信度建议，不能单独决定完成或回滚。

| 可核对情况 | 下一步原则 |
|---|---|
| 编辑格式非法、未应用 | 同一执行阶段做已有有界纠错；不花一次重诊来处理JSON格式。 |
| 当前源码编译／启动失败，有绑定源码的错误 | 先修具体实现；失败若否定了必要前提，再重审计划。基础设施故障不能推断源码有错。 |
| 已接受计划仍合理，实际目标行为没有实现 | 交回 TopoMen 续修，保留具体失败观察和接受意图。 |
| 计划缺少一步／不满足前提，诊断仍绑定当前快照 | 回 ChangeSet。若源码已变导致诊断过期，按已有保护重新诊断。 |
| 同一可比较目标持续无改善，或新证据质疑原因 | 回 Diagnosis 重新评估；不把阶段选择当作已证明原因错误。 |
| 原来已通过的固定需求／保持检查变成失败 | 拒绝退步试验，真实回滚至上一候选；试验日志保留历史快照，不能冒充恢复后状态。 |
| 观察不完整、输入／环境不一致 | 不声称改善或正确；保留可核查候选并解释未验证部分。 |
| 目标和保持义务已在当前快照获得所需公开支持，未解决项已处理 | 结束公开修复流程；独立评价保持独立。 |
| 额度耗尽或无新材料／新进展 | 有界停止并导出明确选中候选；不是把最后一次改动自动视为最好，也不是强迫150条都成功。 |

候选保护需要同时修两点：让正式 benchmark 入口明确接入既有比较器；让保护集合来自同一任务、场景、输入、环境下适用的固定公开需求检查与已确认保持义务，而不完全依赖模型是否记得列出。不要把任意日志里的 PASS 或任务要求改变的旧行为锁死。当前比较器已经核对快照、probe、输入和环境身份，可复用而非重写。

已有正确保护应保留：局部 PASS 不清空更广义务；编译通过不代表行为正确；回滚恢复代码与当前观察，而失败试验仍作为历史材料；未知响应不自动重发；旧诊断不能直接用于新快照。

**7. 与现有150条公开数据如何适配**

本轮检查的是 public/manifest、task、公开执行说明与需求文本，没有读取隐藏评价器或标准补丁。150条在R1–R5各30；运行环境声明归类为Go106、Helm30、Python8、Node3、自定义C构建器2、Maven1。它是运行环境统计，不等于源码语言统计。112条给出多个可编辑路径模式，说明入口必须支持多路径，不能推断112条都需要跨文件修改。

**9. 收敛后的执行计划与验收**

1. **先修已经有反例的边界问题，并核验真实入口。** 交付失败状态统一、空白提示校验、异常轮次与门槛记录；接入既有候选比较并核对保护集。复用模块，不加模型标签。用相同公开fixture验证问题消失，既有正确快照和保留行为继续成立。
2. **完成材料生产和必要性规则的最小修改。** 一个完整物化函数覆盖初选与补证；两处词法强制路径共同收窄；保留已采用材料和已送达约束的适用性审查。每类修改有独立提交／回放证据，最后整合候选完成规定工程检查。
3. **冻结后验证配置和真实效果。** 同源码对照容量；诊断每轮纠错政策如需改变，单独比较。容量、代码、纠错和回退策略的收益不得混称。对原固定面板保留所有失败和退步，必要时用未调参案例检验泛化。
4. **最后按剩余执行失败决定是否加入有限自主查阅。** 先复用现有搜索、读取、编译能力和统一账本，比较同预算的单步与多步；不让自主能力掩盖前半程材料或路由缺陷。
