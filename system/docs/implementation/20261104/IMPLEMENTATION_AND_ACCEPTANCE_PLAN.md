**工作包1：保证最终留下正确的候选，停止原因如实记录**

要解决：新补丁退步后仍替代上一候选；未送达显示为模型缺证据；容量原因不清；异常丢轮次。对应原8、9、10和新发现第一项。

实施顺序：

1. 在后续正式benchmark运行配置／能力入口明确启用现有候选比较器；核对实际使用的runner，不通过伪装isolated runtime触发保护。
2. 固定公开任务契约中适用的检查集合，与当前有效保持义务共同组成保护集合；不完全依赖模型选择，也不锁死任务明确要求改变的旧行为。
3. 复用已有checkpoint、TrialSession、compare_candidate_checks和restore_candidate。回滚后，源码、当前观察、反馈及导出结果均指向选中候选；失败试验保存历史身份。
4. 统一已有EVIDENCE_DELIVERY_INCOMPLETE投影；为请求容量、源码支持、前置审查数量保留实际门槛及数值；try前初始化检索轮次，异常返回保留已有记录。

主要文件：`execution/public.py`、`orchestration/repair.py`、`candidate_guard.py`、`runner.py`、`contracts/status.py`、`retrieval/candidates.py`及运行配置。

必须通过的验收：

- 经实际benchmark入口解析后的保护状态和保护集合可核对，不能只测合成runner。
- 同一退步fixture由“导出退步补丁”变为“真实恢复并导出上一候选”；允许的目标行为变化不被错误回滚。
- 过期／不同环境／不完整观察不被当作可比较PASS；恢复失败不导出假装恢复成功的候选。
- 未发送交付失败在front、repair和最终投影中一致；真正模型证据不足仍为EVIDENCE_GAP。
- 早期异常、补查后异常保留真实轮次；不同容量门槛可区分。

通过后的结论仅是“候选选择与记录边界修好”，不能宣称模型修复率已提高。

**工作包2：让被采用材料完整、相关且能够一致准入**

要解决：材料最初就不完整、在补全之前被淘汰、普通线索变成强制项、选择与采用额度不一致。对应原1、2、3、4、5。

实施顺序：

1. 复用一个完整声明生产函数，在初始`build_candidate_set`前和新增补证`extend_once`前使用；最终`fit_diagnosis`检查一致性与整体容量，不能到这里才第一次补全文。
2. 仓库内容来自固定snapshot；声明输入来自artifact.content；外部API来自已核验依赖版本。同名路径不能替换来源。
3. 首次完整声明生成与其全文匹配的ID、locator、digest和引用边。已采用旧材料保持原身份和正文；新增正文按已有扩展路径准入，不能原地换体。
4. 同时取消runner中纯词法required ID注入、收窄`requires_gap_delivery`中的纯SOURCE_CONTRACT/READER强制性。合并逻辑复用同一判断。
5. 相同容量维度使用同一配置；条数、字节、单请求和总预算仍分别检查。不为容纳新材料删除旧已采用材料；未发送可选项可整体不准入。
6. 保留已经完成的KPT/Helm取材修复，只检验其交付和兼容性。

主要文件：`source/units.py`、`parsers.py`、`orchestration/runner.py`、`retrieval/candidates.py`、`diagnosis/evidence.py`；保留现有`go_context.py`、`dependency.py`和`gap_delivery.py`能力。

必须通过的验收：

- 超80行、超16000字符声明，关键尾部出现在最终请求；无法整体准入时明确报告原因。
- 初选和补证两入口、同名不同receiver、repo/artifact同路径、CRLF/非ASCII、读后快照变化均符合真实身份。
- 纯同名提示不再制造必达端点；显式required、anchor、混合角色和lifecycle保护继续有效。
- 已送达源码约束继续接受ChangeSet适用性审查，不能自动填NOT_APPLICABLE；已采用正文和保持证据跨阶段完整。
- KPT四段函数、Helm三条API仍实际送达；仅增加文本量不作为通过证据。

通过后的结论是“材料生产与准入符合约定”。是否提高诊断和整案效果在工作包4验证。

**工作包3：一个入口决定下一步，诊断纠错只处理真正需要纠错的内容**

要解决：多个模块给出互相覆盖的动作、局部改善被无关联规则重置、不可行动的缺口消耗取材额度。对应原6、7、10和新发现第二、第三项。

实施顺序：

1. 先把现有决策优先级写成整链行为用例；将现有判断等价收拢到一个最终决策入口，不同时改变策略。
2. 使用包1选中的当前快照、真实反馈、保持／未完成义务和现有预算。repair执行决定，不在下一轮再次无声覆盖。
3. 单独核验前提重审的适用性。与失败无关联的前提不应仅凭存在就重置局部进展；相关前提被新证据否定、旧诊断过期等保护仍保留。策略变化须有实际循环反例与真实效果检查。
4. 缺口至少有一个非空白定位字段；空提示在现有校验／格式纠错处理，不花取材额度做空搜索。
5. 对多端点关系等错误返回准确校验位置；不自动拆关系或编造因果解释。澄清现有共享扩展纠错范围；默认保持次数不变，增加次数只作为独立实验。
6. 保留EXPECTED_MISSING与已有新建helper路径，核验它能利用真实缺失搜索、调用点和权限。模型仍反复寻找不存在实现时，按真实回复分析，不删除真实性要求。

主要文件：`orchestration/feedback.py`、`transitions.py`、`repair.py`、`runner.py`、`state.py`、`contracts/validation.py`、已有Diagnosis/ChangeSet schema与校验入口。

必须通过的验收：

- 同一事实只有一个最终动作；记录动作与实际派发一致，回滚后不会拿失败快照覆盖当前路线。
- 编辑格式问题进入有界执行纠错；有效诊断下的计划问题回ChangeSet；证据否定原因或无进展才按规则重诊。
- 局部进展＋无关联前提失败不会被无条件重置；相关前提失败仍能触发必要重审；未完成义务不因局部PASS关闭。
- 诊断快照过期仍重新诊断；执行续修保留接受意图但重新绑定当前源码；UNKNOWN不会显示成完成。
- 空提示不消耗取材额度；始终非法输出在现有限额内停止；调用和费用只有现有账本计数。

第一阶段收拢应保持原行为等价；策略改动单独记录。第三项新发现是否带来效果提升，不能由路由测试代替真实验证。

**工作包4：冻结后验证真实效果、容量收益与完成条件**

要解决：工程测试通过却没有稳定真实收益；容量、代码和重试变化混在一起难以归因。对应原3及全部修复的整体验收。

实施顺序：

1. 每个工作包先通过必要针对性回归；整合候选完成规定工程检查和独立复核后，冻结源码、配置、公开输入及运行入口。旧源码、旧登记、失败结果与账本保留。
2. 比较旧版与新版时使用相同容量、模型及预算；这衡量整组工程修改效果，不能伪称每个细小修改都有独立模型增益。
3. 比较容量时使用同一新版源码与相同其他策略，分别使用原容量和扩容。可将两种比较组织成“旧版原容量／新版原容量／新版扩容”三组，共用新版原容量对照，避免重复付费；具体登记绑定实际完成的候选。
4. 先使用现有固定八案例，保留全部胜、负、共同失败和终止原因。对敏感胜负做必要复核；在未用于调参的公开案例验证收益是否超出已反复调试的八例。样本与对照规则在派发前固定，不看隐藏答案挑案例。
5. 全部调用沿用累计¥100授权并逐次检查硬上限。预算不足时保留未完成验证状态，不能因额度将用完就宣布完成。

必须报告：独立行为通过数、成对改善／退步、进入执行前的停止原因、候选回退保护、完整交付、调用／真实usage／费用／耗时。必须分开“工程缺陷关闭”“准入解除”“真实修复成功”。新样本很少时不声称统计显著或已经普遍稳定。

容量验收：同一必要材料在扩容后得到完整准入，停止原因准确；是否修复成功另报。采用扩容配置还须看实际效果和成本，不能因为能放更多内容就默认更优。

正式实验就绪验收：包1–3的确定性缺陷和完整交付条件全部通过；真实冻结候选相对对照有可核查收益，关键退步已解释或修正，至少在未调参公开案例得到检查；预算与终态可解释。若只通过工程检查、只多送文本或只多通过一个反复调试的案例，仍不能宣布整体优化完成。无需150/150，不要求Dapr等特定难例必须通过。

TopoMen多步自主排查的决定：**本轮暂不扩大权限。** 只有包4显示进入执行后存在可通过搜索／读取／编译解决的共同失败，再做同预算的独立实验。它不是前面三个工作包的前置条件，也不是本轮关闭确定缺陷的完成门槛。
