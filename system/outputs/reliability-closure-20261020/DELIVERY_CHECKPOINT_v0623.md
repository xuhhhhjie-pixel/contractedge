# 0.6.23 优化与验收截点

646项测试、22项子测试在隔离副本和主工作区均通过。源码冻结摘要 `9ac7c0baab790eca5461ae75eea24f36235a9f8bbd3ec09b36da791a0529e75c`；模型、Top12、一次补证、12次调用、两次新鲜语义编辑、请求预算和150元共享账本保持原设定。正式150及消融未启动，`formal_ready=false`。

## 已完成的实际优化

1. 公开失败现在覆盖“没有运行异常但行为错误”的情况。完整、摘要相符、检查身份/状态相符的观察可进入失败任务，携带实际值、公开预期、场景、探测摘要和快照。最多8项/8192字节；超限明确记数，不截断JSON或伪造完整语义判断。
2. 普通主循环与共同续修worker的回退决定都能触发现有执行推理策略，前提是当前恢复快照、失败试验快照、回退决定和失败事实匹配。错误或矛盾身份不触发；原空推理/截断回退规则仍优先，未新增调用额度。
3. 将请求中的重复记录改为严格引用。只有唯一的公开观察ID、快照、内容摘要、位置均一致，且正文摘要核验通过，才共用同一完整记录。只有与已接受计划规范摘要相同的义务谱系和公开能力对象才共用JSON Pointer。原始验证后的反馈和计划不变；待办、保持项、历史失败实际值、完整反馈摘要均保留。
4. 回退决定的解释随REJECT_REGRESSION、UNCOMPARABLE和PROMOTE分别生成，不再在明确回退时仍显示“没有已知回退”。判定及晋级规则未改变。

这是对现有ExecutionFeedback、执行请求组装和候选保护记录的补齐，未新增分析Agent或全仓调用图。

## 为什么需要第三项

0.6.22新鲜KPT成功，但真实保存失败续修首个试验引入保持回退。系统恢复原候选后，第二次请求超出220000上限，未能发送。长历史路径回放也复现了这一点。若只保留失败事实而不处理重复上下文，诊断和执行仍可能无法使用这些事实。

逐字段核查发现：完整公开观察已经在请求正文中，反馈又重复了40份身份/位置记录；义务谱系和公开能力也同时完整出现在已接受计划与反馈中。现在只对规范身份完全一致的对象共用引用，保留不相同或有歧义的记录。
